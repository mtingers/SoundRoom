# Recovered-take authority foundation

This is a **host-only Mac service foundation**, not an enabled recording feature or a new remote operation. It integrates the engine's real raw packet recovery into the same authored authority, receipts, cancellation, and history used by normal edits. Device start/stop and client review flows are still pending.

A trusted hardware/recovery owner relinquishes archive write authority and calls `Service::adopt_raw_capture` on a worker with a retained `PrivateDirectory`. The service reads the known archive files through that handle, checks native manifest bounds, and streams SHA-256 fingerprints before assigning an opaque source UUID. A duplicate raw take identity must have exactly the same custody fingerprints. An absent or unfinished completion receipt remains eligible for explicit incomplete recovery.

`Service::submit_recovery` requires a current authenticated operator and a `service::recovery::Request` with that source UUID, server-selected route/trim/loop plan, every target track's expected version, and an explicit reviewed-incomplete decision. Client paths and client-provided recovered tracks are never accepted. This API is not reachable through the existing wire command decoder. A future remote operation requires canonical grammar, role policy, and a concrete review workflow first.

The recovery worker verifies sealed source fingerprints, calls `recover_take_in`, verifies each published artifact's SHA-256, and decodes its admitted file handle as canonical 48 kHz stereo float WAV. It prepares the complete candidate, checks source references, strict language-neutral snapshot models, the 64 MiB document bound, and authored history. At commit it rechecks credential/role, target/source revision, the old media catalog and source stamps, raw custody, and the actual artifact directory entries against retained file handles. Authority and catalog registration commit together; cancellation, stale state, revocation, changed custody, or failed validation leave both unchanged. Subsequent publication or graph preparation failure cannot reject an already accepted authored edit.

Recovered audio becomes retained `RecordingTake` content. Existing playable clips, comp, effects, mixer, automation, and clip history are preserved. Only a deliberate later comp selection changes playback. Raw provenance stays in the held recovery report; canonical `RecordingTake` remains exactly `id`, `name`, and `clips`. Exact canonical take equality is checked before temporarily rehydrating provenance for the engine's idempotency helper. The normal request ledger returns exact accepted retries without reexecuting; a new request for an already present verified take is a no-op. Undo/Redo affects the take transaction while media remains available.

Storage admission precedes recovery writes. The current host permits at most 32 registered raw sources with 2 GiB total known archive data, 32 retained recovery directories, 32 routes per operation, and an 8 GiB retained recovery/output reservation ceiling. The existing 8 GiB media catalog estimate is also checked. A conservative estimate allows up to eightfold native-rate expansion, stereo channel expansion, 4096 segment headers, and the engine's 16 MiB report. Pending folders and bytes are reserved; failure releases worker reservations. A successfully published but unreviewed or rejected artifact stays charged for review. If cleanup cannot be proved, its conservative reservation remains charged rather than becoming an unaccounted orphan.

## Qualified here

Six pure service tests use real `CaptureArchive` packets, output-anchor journals, streamed recovery WAV files, complete candidate validation, and actual `Authority` history. They cover accepted import plus project save/reopen, exact and new-request deduplication, Undo/Redo, explicit incomplete/missing-completion review, stale/revoked/cancelled preparation, changed raw content and replaced artifact directory entries, private alias rejection, and prewrite quota/version rejection. No device is queried or opened. The separate dense 100,000-point service regression now verifies callback-confirmed Play and Stop after compact engine automation admission.

## Remaining integration and qualification

- Actual hardware stop success, producer sealing/drain proof, archive finish, and lifetime ownership must precede adoption. This API currently trusts its internal caller's relinquished-write boundary; it cannot prove a device has stopped.
- Recording plan/clock/punch authority, Record/Stop receipts, dropout review, source selection, MIDI capture, and client-facing reviewed recovery are not enabled by this checkpoint.
- Opaque source registration, recovery accounting, and registry leases are currently process-local. Startup custody discovery, durable authored recovery receipts, crash reconciliation, retention cleanup, and restart resource budgets remain required before production recording recovery.
- The prepared authority token conservatively fences the whole source revision. Independent-resource concurrency parity remains open.
- Existing media/render/save/export catalog consumers still use their established path facade. Held-handle custody is used for recovery admission and retained artifacts; migrating all later media consumers to the same capability interface remains open.
- Small root/custody metadata operations and source-context capture remain on the serialized owner. Filesystem stall admission, large-token installation/destruction, and optimized control latency during actual recovery need separate qualification; this is not a 5 ms latency claim.
- Owner-only storage rejects aliases, symlinks/reparse entries and unsuitable ownership/ACLs. A malicious process running as the same OS identity is outside that permission boundary; length/identity/mtime rechecks do not claim to defeat same-owner timestamp forgery.
