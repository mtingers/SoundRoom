# Private recording custody

`soundroom-platform` is a low-level worker-only crate, shared by the engine and client. It has no GUI, server, protocol, network or audio dependencies. The existing Windows client API delegates to its extracted owner/DACL provider and preserves policy-error classification.

`PrivateDirectory` is an opaque capability backed by a retained directory handle. `open_root` accepts an absolute configured path with no dot aliases or symlink/reparse traversal, and verifies the final owner-only directory. `create_root` exclusively creates the final component; it never changes an existing directory's permissions or ACL to make an unsafe source look private. Child operations accept one validated UTF-8 name rather than a path. Names reject separators, drive/stream syntax, dot aliases, reserved Windows device names and trailing dot/space normalization.

On Mac/Linux, descendants use `openat` with `O_NOFOLLOW`, `O_CLOEXEC` and directory/type admission. Created directories/files use `0700`/`0600`. Open files must be regular, single-link, owned by the effective user and have no group/other permission bits. macOS additionally checks the extended ACL on the held descriptor: an existing ACL with entries rejects, even if the mode still says `0600` or `0700`. No existing ACL is silently repaired. Linux filesystem and ACL qualification remains a target gate.

On Windows, child creation/opening uses [`NtCreateFile` with `RootDirectory`](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) and `FILE_OPEN_REPARSE_POINT`, then verifies the returned handle. Each new child receives an explicit protected current-process-user DACL instead of relying on inherited ACLs. The policy retains the existing audited requirement: current-user owner, protected DACL, exactly one owner-only allow ACE, no inherited/broad/object/deny ACEs, no reparse node, regular files with one link and noninheritable handles. Read sharing excludes writers/deleters. A sibling publication uses [`SetFileInformationByHandle` / `FILE_RENAME_INFO`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info), addressing the retained source object and retained destination parent with replacement disabled. Local drive paths are supported by the source adapter; UNC storage is explicitly rejected.

## Engine interfaces

- `CaptureArchive::create_in(parent, child_name, manifest)` creates raw metadata, native packets, event journal and completion files through the admitted root. The path compatibility wrapper creates an absolute new private root with the same provider.
- `CaptureArchiveReader::from_directory` and `CaptureEventReader::from_directory` consume admitted file handles; their existing format-only path readers remain available for standalone fixtures/file inspection.
- WAV/AIFF/shared media `from_file` reader/writer constructors and `import_audio_from_files` avoid reopening checked paths. A writer requires a new empty owned file and never truncates an existing artifact. Handle-based import leaves unpublished artifact disposal to the caller's stage.
- `recover_take_in(raw_directory, destination_parent, child_name, plan, cancel)` hashes, scans, writes and verifies through capabilities. `recover_take` is the strict path wrapper and requires absolute private raw and destination-parent directories. Windows no longer has a blanket source-code `Unsupported` recovery branch; hardware Record/service capability remains gated separately.

Raw files retain their original bits and remain under the caller's immutable lease. Recovery publishes synced WAVs and a synced checksummed receipt only after its source fingerprint recheck. Artifact directories and receipts use private child creation on every platform. Same-parent publication refuses existing targets, checks retained source identity before and after publication, and validates identical concurrent/retry receipts. Unix publication uses exclusive `renameatx_np` or `renameat2` relative to the retained parent and syncs that parent afterward. A retry syncs the parent before returning `AlreadyPresent`.

Failed stages remove only their recorded created files, checked empty Audio child and checked own staging directory. Unknown files, changed identities and failures after rename retain artifacts for review. Cleanup never recursively follows a caller-supplied path or deletes a published directory through a stale name.

## Qualification and boundaries

Six Mac filesystem tests cover unicode files, exclusive creation/publication, identity-checked cleanup, symlink/hardlink/FIFO admission, broad mode bits, a real synthetic extended ACL, path replacement and stale stages. Two engine tests cover raw link/permission admission and recovery after the raw path is replaced: the retained capability still reads the original archive and leaves the foreign directory unchanged. The original recording alignment, CRC-tail, stable UUID/hash, concurrent/idempotent recovery and fixed fixture tests remain intact.

Media tests additionally cover handle-based channel-route import/export, source-handle rewind, refusal to truncate an existing output and an original source handle retained after its name is replaced by a symlink. These tests verify original samples and unchanged foreign content.

`tools/check-windows-storage-source.py` type-checks and lints the actual provider against cached Win32 declarations on Unix, substituting only std's OS-string/raw-handle glue. It never links or runs Win32 functions and is **not** a Windows target build or runtime qualification. Windows-specific protected-child/inherited-ACL/hardlink tests are retained for the actual target. Actual Windows and Linux toolchains, filesystem/link/ACL behavior, long paths and crash recovery still need qualification.

File `sync_all` is required before publication. Mac/Linux directory syncs are exercised here. Windows directory `FlushFileBuffers` has no universally supported durability contract; the adapter verifies the directory rather than claiming that a directory flush occurred. Atomic handle rename plus flushed child files is the current Windows source behavior. Power-loss namespace durability remains an explicit Windows/filesystem gate before claiming equivalent durable recording operation.

The trusted principal is the service account. Directory capabilities prevent path/ancestor redirection; owner checks exclude other principals. They cannot stop a compromised process with the same UID/SID, administrator/root or kernel access from changing that owner's files or permissions. Unix lacks a portable rename-by-directory-handle operation, so a malicious same-owner basename swap can race pre/post identity checks; failures retain uncertain artifacts, and no stronger isolation claim is made. The service must serialize cooperating jobs, keep raw/media immutable leases, recheck content hashes and revisions at authored commit, enforce global memory/disk/CPU admission, and coordinate uncertain-result recovery. Client-provided filesystem paths never acquire these capabilities.
